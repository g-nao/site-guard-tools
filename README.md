# site-guard-tools

WordPress・PHPサイトやサーバー上のファイルに、Webシェルや難読化バックドア、
不審なリンクが仕込まれていないかを点検するツール一式です。

- **コードを一切実行しません。** 機械的な変換を静的に解析・展開するだけです
- **Python 標準ライブラリのみ**で動作(Python 3.9 以上)。追加インストール不要
- 誤検出を抑えるため、正規のプラグイン・テーマ・ライブラリと本物の不正コードを区別する設計

> ⚠️ 自分が管理権限を持つサイト・サーバーにのみ使用してください。

---

## 設計思想

このツールは、実際に侵入されたサイトの調査と、他サイトの一斉点検という
現実の作業から生まれました。その過程で得た次の方針を軸にしています。

### 1. 絶対にコードを実行しない

マルウェア解析でコードを実行すれば、それ自体が感染・被害の引き金になります。
本ツールは `eval` も `system` も呼ばず、base64・gzip・hex・rot13・文字列反転・
`chr()` 連結・`\x` エスケープといった **機械的な変換だけを静的に逆算** して中身を暴きます。
実行時に鍵を計算して復号する型は展開できませんが、その場合も「難読化されている」
という事実は検出に残ります(見逃しにはならない)。

### 2. 「キーワードの有無」ではなく「データの流れ」で判定する

`eval` や `base64_decode` は正規のプラグインでも日常的に使われます。
これらの単語があるだけで警告すると、正規サイトで何百件もの誤検出が出ます(実際に出ました)。

そこで本ツールは、**リクエスト値($_POST 等)が実行シンク(eval/system/include)へ
流れ込んでいるか**、**実行関数の括弧の中にデコードが入っているか** という、
本物のバックドア特有の「データの流れ・近接」を見ます。
離れた場所に eval と base64 があるだけでは警告しません。

### 3. 正規の配布物は「公式との一致」で白を確定する

見た目が怪しいかどうかより、**公式配布物と1バイトでも違うか** が最も確実な判定です。
WordPress 本体は公式チェックサムAPIと照合し、一致したファイルは中身が何であれ正規として
以後の警告を抑止します。`vendor/`・`third-party/`・`minify/` などの同梱ライブラリも
正規側に寄せて重大度を下げます。

### 4. 誤検出(ノイズ)を敵とみなす

警告が多すぎるツールは「オオカミ少年」になり、本物を見落とします。
重大度を **高(本物の疑いが濃い)/ 中(要確認)/ 低(記録目的)** に分け、
`--strict` で「確実な異常」だけに絞り込めるようにしています。
実運用では、数百件の誤検出を一つずつ潰して実質ゼロまで追い込みました。

### 5. 見逃しと誤検出のバランスを、利用者が選べる

初期調査では見逃しを最小にしたい、定期点検ではノイズを抑えたい——
場面によって最適点は違います。`--strict` の有無と重大度の三段階で、
利用者が「どちらに振るか」を選べる設計にしています。

## 構成

| ファイル | 役割 |
|---|---|
| `php_malware_scan.py` | サーバー内のPHP/JSを走査し、難読化された不正コードを検出・静的展開 |
| `link_audit.py` | 公開中のサイトを巡回し、不審なリンクやクローキングを検出 |
| `scan-all.sh` | 複数サイトをまとめて点検するラッパー(手動/cron両対応) |
| `sites.conf.example` | `scan-all.sh` 用のサイト定義サンプル |
| `test_*.py` / `test_scan_all.sh` | テスト(下記参照) |

## php_malware_scan.py

```
python3 php_malware_scan.py <対象ディレクトリ>
sudo python3 php_malware_scan.py /var/lib/docker/volumes/xxx/_data --wp-core --wp-locale ja --strict
```

主なオプション: `--strict`(確実な異常だけ高に) / `--wp-core`(WordPress本体を公式チェックサムと照合) /
`--wp-locale ja` / `--since YYYY-MM-DD`(指定日以降に更新されたファイルに印) /
`--unpack-dir DIR`(難読化を剥がした中身を保存) / `--all`(PHP/JS以外も解析) /
`--allowlist FILE`(確認済み正規ファイルを除外) / `--write-allowlist FILE`(今回の高を除外リストに書き出す)

検出するもの: リクエスト値を eval/system/include に流すバックドア、関数名を文字列連結で隠す型、
既知Webシェルの痕跡、多層難読化(base64/gzip/hex/rot13/chr()/\x を何重でも静的展開)、
画像に偽装したPHP、uploads内のPHP、.htaccess の危険設定、(--wp-core時)本体ファイルの改変。

重大度: **高**=本物の疑いが濃い / **中**=要確認(正規のことも) / **低**=記録目的。
終了コード: `0`=高なし / `1`=高あり / `2`=起動エラー。

## link_audit.py

```
python3 link_audit.py https://example.com --allow cdn.example.net
```

隠しリンク、スパム語句、外部script/iframe、JSやmeta refreshによる転送、短縮URL、
内部リンク切れなどを検出。`--user-agent googlebot` で検索エンジンを装い、通常UAとの差分を取ると
クローキング(検索エンジンにだけ見せる改ざん)を発見できます。

## scan-all.sh — 複数サイト一括点検

```
cp sites.conf.example sites.conf   # 初回だけ。自分のサイトを定義
./scan-all.sh                      # 全サイトを点検
./scan-all.sh --cron               # 前回から新しく増えた「高」だけ通知
./scan-all.sh --site KEY           # 特定サイトだけ
```

`sites.conf` に `キー|種別|ロケール|パス` の形式で対象を書きます(詳細は `sites.conf.example`)。
種別は `wp`(WordPress・本体照合+strict)か `static`(中身スキャンのみ)。

### 定期実行(cron)

```
55 4 * * 1 /path/to/scan-all.sh --cron >> /path/to/scan-logs/cron.log 2>&1
```

root専用ディレクトリを読むため sudo が必要な場合、cron では対話入力できないので、
スキャナーの実行だけを対象にした sudoers 設定(`NOPASSWD`)を併用してください。

## 感染が見つかったときは

稼働中のサイトで感染ファイルが見つかっても、その場で消さないこと。攻撃者は複数箇所に仕込むため、
個々のファイルを消すより **クリーンな状態から作り直す** 方が確実です。まず `--unpack-dir` で
中身を保全し、侵入経路(古いプラグイン、弱いパスワード等)を塞いでから復旧します。

## 確認済みファイルの除外(allowlist)

スキャンで「高」と出ても、中身を確認して正規だと分かるファイル(本体の一部、
セキュリティプラグインの設定など)は、繰り返し警告されると本物の異常が埋もれます。
そこで、確認済みファイルを **パス + 中身のSHA256ハッシュ** で除外できます。

```
# まず一度スキャンし、高の検出を除外リストに書き出す
python3 php_malware_scan.py /path --strict --write-allowlist allow.txt --out r.csv
# allow.txt の中身を確認し、本当に正規のものだけを残す(各行『SHA256␣パス』)
# 以降はそのリストを渡すと、該当ファイルは高から外れ「低(許可済み)」として記録に残る
python3 php_malware_scan.py /path --strict --allowlist allow.txt
```

**ハッシュで照合するため、登録後にファイルが1バイトでも変われば除外は自動的に外れ、
再び「高」に出ます。** つまり除外しても改ざん検知は失われません。
`scan-all.sh` は各サイトの `scan-logs/allowlist-<キー>.txt` を自動で読み込みます。

なお WordPress 本体の照合(`--wp-core`)による「本体ファイル改変」は、
本物の本体改ざんを見逃さないため allowlist では除外しません
(`version.php` はロケールで中身が変わりうるので、その旨の補記が付きます)。

## 既知の限界

- 外部CSSによる非表示や、JavaScriptが後から挿入するリンクは検出しません(静的解析のため)
- 実行時に鍵を計算して復号する型の難読化は展開できません(ただし「難読化されている」事実は検出)
- ヒューリスティックな検出のため、正規コードを拾うことがあります(`--strict` で抑制可能)

## テスト

このツールはセキュリティ用途のため、テストを特に重視しています。
合計 **125件**(Python 115 + シェル 10)を備え、次の 9 つの視点で品質を検証しています。

```
python3 test_php_malware_scan.py     # 1. 機能・誤検出
python3 test_robustness.py           # 2. 堅牢性・実在の攻撃手法
python3 test_property_adversarial.py # 3. 性質ベース / 4. 敵対的(検出回避)
python3 test_integrity_regression.py # 5. 内部整合性 / 6. 回帰・スナップショット
python3 test_allowlist.py            # 7. 確認済み除外(allowlist)
python3 test_link_audit.py           # 8. クローラー
bash   test_scan_all.sh              # 9. ラッパーの振る舞い
```

### 1. 機能・誤検出テスト(45件)

- **真陽性**: 本物のバックドア(リクエスト値→実行、多層難読化、画像偽装、既知Webシェル、
  preg_replace /e、uploadsのPHP 等)を確実に「高」と判定するか
- **偽陽性**: 実在する正規のプラグイン/テーマ/ライブラリ
  (WordPress本体・cocoon・updraftplus・phpseclib・All In One Security・
  翻訳キャッシュ `*.l10n.php`・minify・jQuery 等)を「高」にしないか。
  これらは実際の点検で誤検出したパターンをそのままテストに取り込んでいます
- **strictモード**: 確実な異常だけを高に残し、ヒューリスティックな判定を中へ降格できているか

### 2. 堅牢性・実在の攻撃手法テスト(15件)

- **壊れた入力で落ちない**: 不正なUTF-8バイト、空ファイル、`<?php` のみ、
  50万文字の1行、NULLバイト混在、バイナリのゴミ、20重の難読化ネスト
- **実在の攻撃**: 関数名の文字列連結(`$f="sys"."tem"`)、二重拡張子(`.php.jpg`)、
  `$_GET` 値の連結、`assert` バックドア、Cookie経由のペイロード、シンボリックリンク

### 3. 性質ベーステスト(Property-based / 6件)

個別の例ではなく「どんな入力でも成り立つべき性質」を、ランダムな入力を大量に投げて検証します。

- **ランダム入力耐性**: ランダムバイト列300回 + ランダムPHP断片300回で、
  例外も時間切れ(ReDoS=壊滅的な正規表現バックトラック)も起きない
  (各ファイルに5秒のタイムアウトを課して検出)
- **ラウンドトリップ**: 任意のバイト列を base64/多層エンコードしても、展開で必ず元に戻る
- **包含関係**: strict の「高」は常に通常モードの「高」の部分集合である
- **冪等性**: 同じ入力を2回スキャンすると結果が一致する

### 4. 敵対的テスト(回避耐性 / 8件)

攻撃者が検出を逃れようとする小細工に、本物のバックドアを見逃さないか検証します。

- 大文字小文字の混在(`EvAl`, `SyStEm`)
- 関数名と括弧の間への空白・タブ・改行の挿入
- コメントの挿入、短縮タグ(`<?=`)、クォート種別(`'` / `"`)の変更
- 画像偽装 + 実行コード、rot13 で包んだペイロード

### 5. 内部整合性テスト(7件)

ツールが自分自身と矛盾しないことを検証します。

- **ラウンドトリップ**: 全デコード関数が対応するエンコードの正しい逆変換になっている
- **重大度の妥当性**: すべての検出は 高/中/低 のいずれかで、未知の値が紛れない
- **包含関係**: strict の「高」は常に通常モードの「高」に含まれる(多数の例で)
- **CSV入出力**: 書き出したCSVが列ずれなく読み戻せ、件数が内部状態と一致する
- **単調性**: `--exclude` を空にすると走査対象が減らない
- **差分の対称性**: 同じ結果を baseline にすると新規検出はゼロになる

### 6. 回帰・スナップショットテスト(4件)

既知の入力に対する判定を固定し、将来コードを変えて挙動が変わったら気づけるようにします。

- **既知マルウェア**(7検体)が常に「高」であり続ける
- **既知の正規ファイル**(5種)が「高」にならない状態を維持する
- 代表的なマルウェアで検出される**種別の集合**を固定(種別名の増減に気づく)
- **多層難読化**が各層を剥がして最深部のバックドアに到達し続ける

### 7. 確認済み除外のテスト(allowlist / 10件)

- 登録したパス+ハッシュが一致する検出だけを「高」から除外する
- **登録後に中身が変われば(ハッシュ不一致)除外しない**=改ざん検知を維持する
- パスが違えば除外しない、壊れた行や存在しないリストでも落ちない
- 除外は消さず「低(許可済み)」として監査証跡に残す
- `--write-allowlist` で現在の高を除外リスト形式に書き出せる(往復で整合)

### 8. クローラーのテスト(18件)

HTMLパーサの挙動(隠し要素の継承、暗黙の閉じタグ、コメント内リンクの無視)、
文字コード判定、IRI→URI変換、sitemap(gzip/index)、クローキング検出、差分(baseline)など。

### 9. ラッパーの振る舞いテスト(10件)

設定ファイルの読み込みと異常系、コメント・空行・CRLF改行の扱い、`--site` 絞り込み、
存在しないパスのスキップ、cron差分検知と終了コード。

### テストスイート全体の整合性

個別のテストだけでなく、全テストを一括実行したときの相互干渉もチェックしています。
実行順序を変えても・ランダム順にしても全てパスし(順序依存なし)、グローバル状態は
`try/finally` で確実に復元され、一時ディレクトリとポートは毎回ユニークに確保されるため、
テスト同士が干渉しません。連続実行で結果がぶれる「フレーキーテスト」もありません。
